# 기획서 반영 범위

기준: 상위 `final_project/` 폴더의 「서울 지하철 출발 시각 추천 서비스 최종 기획서.pdf」, 2026-11-10. 원문 사본은 [final-proposal.pdf](final-proposal.pdf)입니다. 현재 사용자 요청에 따라 혼잡으로 인해 한두 대를 보내는 상황을 추가 요구사항으로 반영합니다. 2026-11-11 범위 결정은 프로젝트의 `진행기록.md`에 근거와 함께 남깁니다.

## 서비스

- 출발역·도착역·경유역 0~2개·목표 도착 시각을 입력합니다.
- 출발 시각은 출발역에서 **승차하는 시각**입니다. 집↔역 도보는 계산하지 않습니다.
- 안정 출발(P95)과 실시간 마지노선 출발, 열차번호, 예상 도착 범위, 환승 연결 확률을 제공합니다.
- 운행 중 열차 위치, 경로상 지연 경고, 계산 결과에 기반한 추천 설명을 표시합니다.
- 혼잡에 따른 탑승 대기를 최초 승차와 환승 승차 모두에 추가합니다.

## 지금 구현한 수집 단계

2026-11-10 2호선으로 시작해 2026-11-11 활용사례 등록 후 **서울교통공사 1~8호선**으로 넓혔습니다(9호선·코레일은 시간표 밖이라 제외). 노선마다 30초 간격으로 위치를 수집하며, 평일·주말 모두 KST 06:30~09:30, 17:30~20:30에 수집하고 날짜·요일별로 보관합니다. 부가로 시간표(매일), 도착정보 샘플(2분), 역별 시간대별 승하차 인원(월)을 수집하고, 역간·환승 소요·역 좌표·열차 혼잡도는 공개 CSV를 적재합니다. 운행 공지·SK 혼잡도·날씨는 기획서 계산에 쓰이지 않아 수집하지 않습니다. 실제 과거 위치 이력은 실행 이후부터 생성됩니다.

API 원천 관측 시각과 PC의 수집 시각을 구분합니다. 같은 행 반복 수신, 순서 역전, 오래된 응답, 관측 공백을 처리합니다. 역 도착은 30초 샘플에서 관찰한 구간이므로 초 단위 실제 도착 시각이라고 단정하지 않습니다. 열차번호·역명·방향으로 당일 시간표를 유일하게 매칭한 경우에만 지연의 상·하한을 계산합니다.

## 혼잡으로 열차를 보내는 상황

소요 시간에 `탑승 대기 = 최초 도착 대기 + 탑승하지 못해 보낸 열차들의 배차 간격 합`을 추가해야 합니다. 입력은 서울교통공사 지하철혼잡도정보(역·방향·30분 단위 평균 혼잡도)입니다. 하지만 차내 혼잡도 통계만으로 탑승 실패 여부를 알 수 없습니다. 승강장 대기열, 하차 인원, 문별 탑승 위치, 열차의 잔여 수용 인원이 필요합니다.

현재 관측하지 않은 `실제 보낸 열차 수`, `실제 승차 성공 여부`는 정답으로 생성하지 않습니다. 이후 사용자 현장 기록이나 승인된 실시간 수집원을 확보한 뒤 탑승 성공 확률을 학습해야 합니다. 임계값으로 계산하는 경우에는 **가정에 따른 시나리오**로 구분합니다. 통계의 0이나 빈 값은 미운행 조합일 수 있어 빈 열차라는 뜻으로 사용하지 않습니다.

## 후속 4주 흐름

| 단계 | 작업 |
|---|---|
| 0일차 | 수집기·요일별 원본·지연 관측값·출처 제약 확인 |
| 1주차 | 실제 키 연동, 데이터 품질·시간표 매칭률, 대상 노선 확정, Kafka, 역/환승 그래프 |
| 2주차 | Flink 궤적/도착/지연 처리, Spark 통계 기준선, Airflow 배치 |
| 3주차 | Redis 현재 상태, LightGBM P50/P95, 환승 분류, FastAPI 경로/출발 시각 계산 |
| 4주차 | 노선도 UI·LLM 입력/설명, 정시율 검증, 리플레이·장애복구·모니터링 |

마지막 1주를 테스트로 남기는 날짜 분할을 사용합니다. 계획용 모델에는 현재 운행 상태를 넣지 않습니다. P95 커버리지·Pinball loss·환승 AUC와 동일 정시율에서 출발을 늦춘 시간을 평가합니다. 구간별 P95 합이 전체 경로의 95% 도착 보장을 의미하지는 않으므로 전체 경로 기준으로 별도 검증합니다.
